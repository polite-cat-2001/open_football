# Каталог команд и экран выбора

**Статус на 2026-11-09:** Godot владеет каталогом лиг, команд и игроков, читая единую
`open_football.sqlite` напрямую и **лениво** (по экранному запросу, как оригинальный
`TeamSelectPage`). C++-каталог для экрана выбора больше не используется; выбранные команды
уходят в матч готовым пакетом — [[пакет-матча]]. Экран выбора команд переведён на
дизайн-систему и общий `TeamSelectView` — [[дизайн-система-ui]]. Контекст трека —
[[порт-gdextension]]; спека набора: `.scratch/gpf-game-shell/spec.md`, тикет —
`issues/04-sqlite-katalog-lig-i-komand.md`.

## Единая БД и один id

- Источник — `<data>/databases/default/open_football.sqlite`, сборка:
  `python tools/build_open_football_db.py`. Инструмент сливает игровую `database.sqlite` и
  `canon.db` карьеры по transfermarkt-id.
- **Один id на сущность:** `countries.id`, `teams.id`, `players.id` — числовой tm_id;
  `leagues.id` — код соревнования (`MEXA`, `ES1`); синтетика — страна `International` (id 1) и
  лига `National Teams` (id `NAT`). Дубли «клуб + сборная» (3 500 игроков) схлопнуты.
- Поля карьеры лежат в той же БД: `players.market_value/overall/pot/birth_date/career_role/stats`,
  `teams.stadium_name/seats/founded_on/colors`, `leagues.tier_name/tier_rank`. Игровые поля
  (`formation_xml`, `tactics_xml`, `kit_url`, `profile_xml`, внешность) сохранены.
- `leagues.legacy_id` — только ключ старых медиа (`images_leagues*`), не идентификатор.
- Состав: 107 стран, 280 лиг, 4 652 команды (4 406 клубов + 246 сборных), 121 927 игроков
  (включая свободных агентов); eligibility пишется рядом в
  `open_football_eligibility.json`, manifest — `open_football_manifest.json`.

## SqliteReader

Почему свой парсер: Godot не умеет SQLite, а тянуть бинарный GDExtension-аддон в публичный
репозиторий ради двух таблиц не хочется. Читатель на GDScript ходит по файлу страницами
(`FileAccess.seek` + `get_buffer`) и разбирает ровно то, что нужно каталогу.

- Поддерживаются только table b-tree (0x0D лист, 0x05 interior), overflow-страницы и все serial
  types. Индексы, views, `WITHOUT ROWID` и запись не поддерживаются.
- `select_all(table, wanted)` возвращает массив словарей; `wanted` отсекает тяжёлые колонки
  (`formation_xml`, `tactics_xml`), которые каталогу не нужны.
- `select_indexed` ходит по индексу; для `INTEGER PRIMARY KEY` (`teams.id`) используется точечный
  поиск по rowid, а не скан таблицы (раньше `team_by_id` стоил ~90 мс). `count_indexed` считает
  строки по одному ключу, `count_index_values` — все ключи индекса за один проход (для больших
  лиг вроде National Teams).
- **Грабли:** только колонка `INTEGER PRIMARY KEY` в payload хранится как NULL (serial type 0), её
  значение — это rowid ячейки. Читатель берёт имя такой колонки из `CREATE TABLE` и подставляет
  rowid. `TEXT PRIMARY KEY` (`leagues.id`) читается как обычная колонка.
- **Грабли:** `country_id`/`tier` бывают NULL (лига `National Teams`), поэтому каталог приводит
  числа через null-safe `_int()`.
- 193 МБ база: лиги+команды читаются ~130 мс; `players` (125 402 строки) — ~3 с, поэтому каталог
  игроков должен читать только нужные колонки/команды.

## TeamCatalog (ленивый)

- Корень данных: аргумент `load_data_root(root)`, иначе `GPF_DATA_ROOT`, иначе
  `DEFAULT_DATA_ROOT` (`C:/Users/Egor/Desktop/projects/GameplayFootball-of_port/data`) — тот же
  порядок, что у `GpfRuntimeNode`.
- Путь к базе: `<root>/databases/default/open_football.sqlite`.
- `load_data_root` **не читает всю базу**: открывает read-only reader, проверяет таблицы
  `countries/leagues/teams/players` и что `leagues` непустая; reader живёт до `close()`/свободы
  каталога.
- `countries()` — страны, у которых есть лиги (как `join leagues` оригинала), сортировка по имени;
  `leagues_for_country(id)` — лиги страны (tier → имя); `teams_for_league(id)` — команды лиги,
  отсортированы по имени. Команды с <11 игроками **отфильтровываются при листинге**.
- **Как это делает оригинал:** `AddTeams` в `teamselect.cpp` отдаёт SQLite один запрос
  `select ... from teams t where league_id = ... and (select count(*) from players p where
  p.team_id = t.id or p.nationalteam_id = t.id) >= 11 order by name` — счёт считает C++-SQLite
  по индексам, 217 сборных листаются быстро. Наш `SqliteReader` не исполняет SQL, а обход
  b-tree в GDScript стоит миллисекунды на команду, поэтому:
  - `python tools/build_open_football_db.py` (или `tools/build_team_eligibility.py`) пишет
    `databases/default/open_football_eligibility.json` (готовые наборы `club`/`national` с >=11
    игроками); `TeamCatalog` загружает его в `load_data_root` и фильтрует по множествам. Без
    файла — fallback: до 32 команд в лиге точечный `count_indexed`, крупные лиги — один
    `count_index_values`.
  - Результат лиги, счётчики и ответы `can_field_eleven` кэшируются по id. Ready-проверка
    остаётся страховкой, а хаб получает только валидные составы.
- `team_by_id`/`league_by_id`/`country_by_id` — точечные запросы с кэшем; `national_league_id()` —
  запрос по имени, кэш.
- `load_squad(team_id)` читает полный состав только выбранной команды; `load_team_rating(team_id)`
  читает только `role`/`base_stat` двух выбранных команд и кэширует по `team_id` (без разбора
  `profile_xml`).
- Ошибки: `Team database not found at <path>. Set GPF_DATA_ROOT...`,
  `Team database could not be read: <path> (<detail>).`, `Team database has no leagues or teams: ...`;
  после отказа каталог остаётся пустым.
- `read_manifest_coverage(root)` читает `coverage` из `open_football_manifest.json`; тест
  проверяет, что данные непустые, и выборки по требованию, а не «в памяти все 4652 команды».

## ShellState и экран

- `ShellState` — статический класс (`home_team`, `away_team`, `set_teams`, `has_selection`,
  `match_options`, `match_package`, `clear`). Статика, а не autoload: headless `-s` не создаёт
  autoload'ы, а тесты должны идти тем же путём, что и игра. Прематч и матч читают отсюда.
- Экран выбора команд — `TeamSelectView` ([[дизайн-система-ui]]): две карточки **HOME/AWAY**
  с блоками **Country / Team / Competition**, флагами/гербами/лого, звёздами и ATT/MID/DEF.
  Отдельного Ready-ряда нет: `A/Enter` на любом блоке делает панель ready, `B/Esc` снимает ready
  или выходит. `Up/Down` — блок, `Left/Right` — значение. При одном устройстве после ready home
  активируется панель CPU-away; при двух локальных устройствах обе панели активны параллельно.
  По ready обеих сторон `ShellState.set_teams(...)` и переход в Kit Select. `V` убран, мышь инертна.
- «National Teams» — специальная первая страна; лига не показывается как отдельный уровень,
  в блоке Competition отображается `National Teams`. Без сохранённого выбора экран открывается
  на **FC Barcelona vs Real Madrid** (Spain/LaLiga); если пары нет в базе — на первой реальной
  стране. National Teams не выбирается стартовым, чтобы не листать 217 сборных без запроса.
- Kit Select — отдельный общий экран между командами и прематчем: четыре комплекта на сторону
  (`HOME/AWAY/THIRD/FOURTH`), 3D-превью матча, ready по панелям; в 1P человек выбирает home, затем
  away. Выбор уходит в `ShellState.kit_home/kit_away`; см. [[дизайн-система-ui]].
- Предматчевый хаб — общий `MatchHubView`: две колонки 11 стартовых, scoreboard с рейтингом,
  command-ячейки **START MATCH / TEAM MANAGEMENT / MATCH OPTIONS / EXIT**. Game Plan
  открывается полноэкранным `GpfGamePlan`, Options — слайдеры сложности/длины и заглушки,
  EXIT возвращает в главное меню. Start собирает пакет (`MatchPackage`) и открывает матч —
  [[пакет-матча]]; в 2P Start — голос каждого локального устройства.
- Если база не открылась, экран показывает сообщение об ошибке; `Enter/A` повторяет загрузку,
  ready не срабатывает.
- Вход: тайл **Quick Match** в главном меню → controller/side select → team select → kit select →
  прематч.
  Встроенной пары команд нет, старый пакет не переиспользуется.
- UI-правило набора: экраны меню портируются из `GameplayFootball-of_port/src/menu/...`, а не
  проектируются заново (см. `spec.md`, «UI-политика» в каждом тикете).

числовой id) и предпочитает эту папку, затем `logo_url`.

Индексы единой БД создаёт `tools/build_open_football_db.py`: `idx_teams_league`,
`idx_leagues_country`, `idx_players_team`, `idx_players_national`. Без них `teams_for_league`
сканировал бы 4 652 команды (~90 мс на каждую смену лиги); с индексами — единицы миллисекунд.
Eligibility — `open_football_eligibility.json`, аналог SQL-запроса оригинала; без файла работает
медленный fallback.
