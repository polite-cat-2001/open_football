# Тестирование UI

**Правило:** ни один экран не считается сделанным, пока его не увидели и не прошли как пользователь.
Headless-тест проверяет поведение, скриншот — вёрстку, живой прогон — ощущение. Нужны все три.

Причина правила: UI, собранный «по коду» без взгляда на экран, оказывается неюзабельным — кнопки
уезжают, фокус теряется, до действий нельзя добраться. Такое уже случалось; после этого методика
стала обязательной.

## Три уровня

### 1. Живой прогон через Godot MCP (обязательный)

Godot запускается с autoload `godot_mcp_runtime` (`project.godot`), поэтому игрой можно управлять
снаружи:

1. `godot_launch_editor` (или `godot_run_project`) — поднять игру.
2. `godot_runtime_get_tree` / `godot_runtime_get_node` — понять, какой экран открыт.
3. `godot_runtime_input` — нажимать клавиши (только клавиатура; см. ограничения).
4. `godot_runtime_screenshot` — снять кадр и **посмотреть его**.
5. `godot_runtime_call_method` / `godot_runtime_set_node` / `godot_runtime_freeze` / step — загнать
   игру в нужное состояние и остановить его для кадра.

Каждый экран проходит путь: главное меню → экран → действие → возврат. Для HUD — форс-состояния
(кикофф, гол, перерыв, серия пенальти, стандарт) и скриншот каждого.

### 2. Headless поведенческие и layout-тесты

Быстрые, без рендера, идут в общий прогон `tests/check_*.gd`:

- **Состояние:** экран получает фикстуру (`UiState`/снапшот), проверяются подписи, доступность,
  включённость кнопок, переходы.
- **Фокус:** из начального фокуса стрелками обходится весь экран; каждая интерактивная кнопка
  достигается, Enter срабатывает, Esc возвращает.
- **Layout:** `tests/check_ui_layout.gd` — при 1920×1080 и 1280×720 ни один интерактивный Control
  не вылезает за viewport, размеры не нулевые, интерактивные прямоугольники не накладываются;
  текстовые Label'ы тоже не выходят за экран (это ловит обрезанные длинные подсказки HUD).

Headless **не рисует** — PNG оттуда пустой. Скриншоты снимаются только в оконном запуске.

## Стенд состояний

`scenes/ui_lab.tscn` — «витрина» HUD и оверлеев без C++:

- `1..9`, `0` — первые десять состояний (кикофф, live, гол, штрафной, перерыв, финал,
  серия, конец серии, пауза, Game Plan), дальше `←/→` — Game Plan 2P, Game Plan Tactics,
  Game Plan Roles, Game Plan Select, notice замены, карточка, set-piece taker (всего 17);
- `←/→` — соседнее состояние;
- подпись с номером/названием состояния (в скриншотах скрывается).

Фикстуры — обычные словари в `scripts/ui/ui_lab.gd`; экран не читает runtime. Это же шов для
будущего Svelte-порта: представление = функция от снапшота.

`GpfHud` и `GpfShootoutView` уже разделены: `setup(runtime)` нужен только для действий,
`apply_snapshot(snap)` / `update(snap, delta)` — для отрисовки. Lab использует `setup(null)`.
`GpfGamePlan` в стенде получает демо-составы через `setup_demo()`; в матче и премате — через
`setup_match(runtime, human_teams)` / `setup_prematch(home, away, human_teams)`.

Для живого прогона MCP есть автозагрузка `UiHarness`: `seed_match()` собирает пакет и сразу
открывает `gpf_slice`, `inject_click(x, y)` (или `pointer` + `click_pointer()`) кликает по UI,
`inject_joy_button/axis` шлёт геймпад. MCP не умеет передавать массивы, поэтому для точных
одиночных нажатий есть no-arg обёртки: `key_tap_code` + `tap_key()` (press и release через кадр,
C++ успевает увидеть кнопку) и `joy_tap_device`/`joy_tap_button` + `tap_joy_button()`.
`GpfGamePlan.debug_state()` возвращает текущие курсоры/held обеих панелей.

### 3. Svelte-прототип как эталон

Прототип в Svelte — источник раскладки и токенов, а не повод изобретать Godot-UI заново.
Перед портом экрана фиксируются:

- матрица состояний (какие бывают и что показывают);
- действия и их привязки (клавиатура/геймпад);
- токены: цвета, шрифты, размеры, отступы.

Godot-экран обязан пройти ту же матрицу; скриншоты сравниваются с веб-прототипом глазами.
Пиксельный дифф не обязателен, пока прототип черновой.

## Шов: UI как функция состояния

Чтобы всё это было возможно, экран не должен сам лазить в C++:

- HUD/оверлеи матча получают снапшот через `apply_snapshot(dict)`;
- меню получают данные через `set_state()` / `ShellState`;
- `scenes/ui_lab.tscn` подаёт канонические снапшоты без C++ (гол, перерыв, серия, 2P, лобби).

Исключение — действия пользователя: они идут в runtime через узкий API (`request_set_piece_taker`,
`begin_phase_break` и т.д.), а не читают его поля.

## Definition of done экрана

- [ ] Скриншоты 1920×1080 и 1280×720, просмотрены.
- [ ] Все действия достижимы клавиатурой **и** геймпадом.
- [ ] Видимый фокус; Esc/Back работает; тупиков нет.
- [ ] Нет переполнений и наложений (headless layout-тест).
- [ ] Состояния из матрицы покрыты тестом/скриншотом.
- [ ] Отступления от оригинала записаны в тикете.

## Ограничения инструментов

- **Godot 4.7: в дефолтном `ui_accept` нет кнопки геймпада** (только Enter/Kp Enter/Space).
  `ui_up/down/left/right` при этом включают D-pad и левый стик. Поэтому каждый экран обязан сам
  обрабатывать A (активация) и B (назад), иначе геймпад «застревает» на главном меню. Проверено
  на чистом проекте 4.7.2.
- `godot_runtime_input` инжектит только `InputEventKey` с одним `keycode`. Этого достаточно для
  экранов, которые сами читают `_input` (controller/team select через `UiNav`, `gpf_slice`), но
  **недостаточно для активации сфокусированной `Button` через `ui_accept`**: Enter/Space не
  нажимают кнопку. Для GUI-кнопок использовать `godot_runtime_emit_signal` с `pressed` (или
  добавить в bridge полноценный key/joypad-инжект с `physical_keycode`).
- Геймпад проверяется через `UiHarness.inject_joy_button()` (вызов из `runtime_call_method`).
- Один C++-runtime на процесс: LAN-тесты запускают **два** процесса Godot.
- C++-рантайм делает `chdir` в `GPF_DATA_ROOT` при старте, поэтому **относительные пути в игре
  пишутся в папку данных GameplayFootball**. Скриншоты и временные файлы сохранять в `user://`
  или абсолютным путём.
- Смена сцены внутри `_input` обнуляет `get_viewport()` у старого узла: запоминать viewport до
  обработки, иначе `set_input_as_handled()` падает.
